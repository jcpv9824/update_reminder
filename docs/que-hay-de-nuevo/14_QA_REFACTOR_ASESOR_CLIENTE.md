## 1. Datos y evidencia

Usar una instancia SQL Server 2019 aislada y usuarios, empresas, documentos, archivos y direcciones ficticios. No utilizar ERP real, SAG Admin real, QA compartido ni producción. Mantener el proveedor de correo y sus workers deshabilitados. Validar respuestas, historial y cambios en SQL además de la interfaz.

- **Actores:** D es autor de Desarrollo; S1 es asesor inicial; S2 es otro asesor con permiso de prueba y toma la entrada; S3 es asesor con permiso de prueba y publicación; S4 tiene área Soporte sin permiso de prueba; A es `super_admin`; P no tiene sesión. Para las pruebas de publicación, usar también una sesión con permiso de prueba pero sin publicación y usuarios inactivos o que perdieron acceso. No cambiar permisos SQL para ejecutar estas pruebas.
- **Entradas:** una entrada elegible para publicación, una crítica, una retirada, una privada y una visible. Sembrar fechas de creación en ambos límites de mes y fechas de resultado/liberación distintas para separar las reglas, más dos rondas y fichas con un asesor inicial distinto de quien tomó y de quien cerró una ronda anterior.
- **Canarios separados:** texto interno, notas, hallazgos, corrección, identidad del equipo, cliente ERP y referencias privadas, y título/descripción/ruta aptos para el público. El dato público nunca debe ser una copia accidental de uno privado; usar valores ficticios y únicos para buscar fugas sin leer contenidos reales.
- **Registro por caso:** SHA del candidato, fixture/sello UTC utilizado, capa observada, resultado, salida reproducible y evidencia sin credenciales. Los estados son `pendiente`, `pasa`, `falla` o `no ejecutado` con motivo. Los resultados de esta ejecución se anotan en la sección 7; una fila no se considera aprobada para todas las capas solo por un subconjunto comprobado.

## 6. Puertas de salida

1. Pruebas enfocadas: frontend `queHayDeNuevoLive`, `queHayDeNuevoAsesor`, `queHayDeNuevoNovedades`, `queHayDeNuevoFormulario` y `whatsNewPrivateEditor`; API `whatsNewCommands`, `whatsNewHttp`, `whatsNewSqlRepository`, `whatsNewSqlWriteRepository`, `whatsNewService`, `whatsNewSavedReports` y `whatsNewDeletionHttp`. Agregar casos con reloj inyectado, latencia y fallas; no omitir el navegador por tener mocks.
2. Validación SQL y reglas de permisos: si hay migración, verificar manifiesto y parser TSql150; en SQL Server 2019 aislado ensayar aplicación, replay y reversión, y confirmar que los checksums antiguos no cambian. Verificar datos existentes antes/después y los invariantes de idempotencia, visibilidad e historial.
3. CI: en ambos proyectos instalación limpia, las dos auditorías, toda la suite y builds; añadir `check:no-cosmos-runtime` en API. Comprobar ausencia de fixtures, rutas demo y configuraciones locales en el bundle.
4. Navegador end-to-end: Desarrollo y dos cuentas de Soporte ficticias, recarga real, notas/hallazgos, aprobación privada y otras combinaciones; abrir público anónimo solo con datos ficticios aislados. Comprobar reporte exacto, no correo y fallas de permisos en HTTP. Registrar lo que no se certifica con servicios simulados (por ejemplo, almacenamiento real o publicación en Azure).
5. La entrega de QA no activa publicación pública, correo ni ningún entorno fuera de esta instancia; esos cambios requieren autorización separada.

La ráfaga de escrituras del primer ensayo recibió HTTP 429; el automatismo respetó el límite sin modificarlo. El ensayo HTTP con SQL real no sustituye por sí solo la revisión de todas las combinaciones UI de mes/recarga, edición simultánea con latencia o de todos los actores y estados descritos arriba.
