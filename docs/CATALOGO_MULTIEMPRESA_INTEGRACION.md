## Flujos integrados

En Conexiones, las acciones de probar y guardar SeaweedFS reciben una instantánea del formulario y de la versión al hacer clic. No dependen de que TanStack Query haya actualizado las opciones de la mutación mediante su efecto posterior al renderizado. Las regresiones conservan deliberadamente la función inicial del observador para comprobar que se envían el destino visible y su ETag, no los valores vacíos iniciales. Las variables de estas mutaciones sólo viven durante la solicitud: se reinicia el observador al finalizar y su caché usa `gcTime: 0`; las llaves no se incorporan a la caché de consultas ni a la documentación. Esta corrección no cambia el proveedor de almacenamiento ni sus permisos.

- **Configuración → Conexiones.** Reutiliza perfiles SQL existentes. El registro distingue los ERP que suministran clientes de SAG Admin. Guardar un vínculo sólo crea un borrador. **Verificar** necesita el permiso de prueba y comprueba TLS, permisos de solo lectura, esquema y una fila como máximo, sin mostrar datos. **Activar** necesita además el permiso de edición, repite la prueba y guarda la certificación sólo si el vínculo y el perfil siguen siendo los mismos. También permite revalidar una fuente activa cuando el perfil cambió; no cambia su rol ni la sustituye. Verificar o activar no publica revisiones ni cambia permisos de la base remota.
- **Clientes.** Vista de sólo lectura, con filtros iniciales Activos y En SAG Web. El selector parte de todas las fuentes ERP autorizadas para quien consulta. Las fuentes fallidas se muestran como desactualizadas o no disponibles, no como clientes inactivos ni fuera de SAG Web. La vista anterior se conserva hasta el corte deliberado; no es un fallback ante errores del catálogo nuevo.
- **Acceso.** Los endpoints requieren sesión y permiso de Portal. Además, el backend comprueba el acceso a cada ERP en SQL, no a partir de los filtros enviados por el navegador. La migración 034 no siembra nuevos accesos. El contrato de lectura no devuelve identificaciones en claro, contraseñas, hosts ni cadenas de conexión.
- **Preparación de una revisión.** El servicio de carga sólo admite vínculos activos del entorno indicado. Exige una lectura externa completa en una transacción `SNAPSHOT` y conserva la diferencia entre «sin registros» y «no disponible». Entrega al publicador la versión del vínculo y del perfil, el identificador interno de fila, el estado normalizado y un token HMAC del documento; no entrega el documento original. Antes de abrir la fuente, SQL asigna un número de intento que ordena resultados concurrentes independientemente de su hora de finalización. Las coincidencias de SAG Admin sólo se consideran de un emisor cuando existe un mapeo revisado, y las filas sin emisor no permiten afirmar que otros clientes están fuera de SAG Web.
- **Actualización explícita por fuente.** `POST /api/settings/integrations/catalog-sources/{sourceId}/refresh` recibe únicamente `{}`. Requiere `super_admin` activo y permisos de ver, probar y editar Conexiones; limita las solicitudes y no abre las demás fuentes. SQL verifica de nuevo operador, vínculo y perfil en cada transacción. Solo una revisión sellada reemplaza la actual y la publicación exitosa audita el ID del operador sin valores del origen. La ruta no modifica la pantalla ni programa ejecuciones periódicas. Para SAG Admin, `PORTAL_CATALOG_SAG_ISSUER_MAP` admite pares revisados `countryId`/`issuerScope`; no permite declarar cobertura negativa desde ese mapa.
- **Evidencia de SAG Admin.** La migración 035 permite sellar y conservar el dominio candidato, el ambiente, las letras de licenciamiento aceptadas y las fechas conocidas de inicio por ambiente. El SELECT emite únicamente el hostname y los tres días autorizados; no devuelve la URL completa ni el JSON original. Ausencia o invalidez se conservan como desconocidas. El hostname por sí solo no habilita una conexión ni acredita una base o un despliegue.
- **Detalle de Clientes.** Dominio y licenciamiento se consultan en rutas separadas con los permisos existentes de cada opción. El backend resuelve el ID opaco del cliente sólo en fuentes ERP autorizadas y cruza revisiones selladas por emisor, tipo y token exactos. La evidencia incompleta se marca; una revisión vencida no se presenta como actual, y una consulta sin coincidencia no acredita ausencia sin cobertura. Dominios se muestran como texto y agrupados por nombre dentro del mismo cliente, con observaciones separadas por ambiente; no habilitan acceso o programación.
- **Inventario independiente.** Dominios, Bases de Datos y Licenciamiento conservan su URL y permiso de lectura y, con el interruptor del catálogo, usan `GET /catalog/inventory/{domains|databases|licenses}`. La consulta SQL limita por actor, fuente y ambiente antes de combinar o paginar. Para vínculos operativos usa nombres oficiales de revisiones ERP verificadas y relaciones 042; Bases de Datos muestra el alias y el nombre público de su dominio padre sin detalles de acceso. Licenciamiento cruza la identidad exacta y sólo presenta una descripción de módulo cuando tiene correspondencia vigente. Un resultado parcial o no disponible no vuelve al maestro anterior, y ningún error de driver se devuelve al cliente. Las rutas CRUD históricas no se deshabilitan por este cambio de vista.
- **Correspondencia de licencias.** Con la migración 041 un operador puede registrar en `settings.catalog_sag_license_module_approvals` una correspondencia revisada de una letra hacia un módulo existente. SQL exige fuente SAG Admin activa y certificada, versiones exactas del vínculo y del perfil, identificador de aprobación y operador. El detalle muestra el nombre y la descripción de módulos activos solo para los códigos observados. Una letra sin equivalencia queda como «Correspondencia no verificada». No se crean módulos ni se sugieren equivalencias por similitud. Las aprobaciones no se sobrescriben; cualquier cambio de la fuente o del perfil exige volver a aprobarlas. El resolver interno solo prepara IDs de licencia cuando el cliente tiene evidencia vigente, el dominio y ambiente coinciden y no hay observaciones ambiguas. No devuelve los IDs internos al navegador ni habilita por sí solo el generador de tareas.
- **Registro físico.** La migración 036 separa cada relación lógica de un destino SQL o web acreditado. SQL usa una instancia certificada y el GUID leído con la cuenta y TLS aprobados; web usa un identificador de despliegue acreditado, no el texto de la URL. Si cambia la ruta se retira la prueba y volver atrás no la rehabilita. Si cambia el perfil SQL, su versión deja de coincidir. La huella histórica del nombre sólo sirve para rechazar una colisión de GUID con catálogos distintos: no permite unir destinos por nombre. Un cambio de nombre SQL necesita un procedimiento de continuidad antes de volver a aceptar el destino; no se reasigna silenciosamente.
- **Vínculo operativo.** La 042 registra por separado el cliente del catálogo, su correspondencia con el maestro operativo y cada vínculo ERP de un dominio o de una base. Los vínculos tienen UUID estable; las aprobaciones no se sobrescriben y se atan a la versión certificada del origen y del perfil. Un refresco normal que conserva el registro exacto activo y la identidad del cliente no cambia el UUID. Si cambia el perfil, se requiere una aprobación adicional; si se retira el cliente o el vínculo, la historia se conserva. El lector interno conserva vínculos abiertos no verificables y rechaza una lectura de más de 5.000 vínculos en lugar de devolver un conjunto truncado. Una aprobación no certifica el servidor físico, no asigna licencias y no otorga acceso a credenciales.
- **Dominios compartidos.** La 043 permite la misma URL HTTPS normalizada en clientes o ambientes distintos. Cada relación conserva su propio ID y las bases asociadas. Una URL no puede repetirse dentro del mismo cliente y ambiente mientras los registros no estén eliminados. El API devuelve un conflicto controlado para esa colisión. La coincidencia de URL nunca une enlaces automáticamente: al planificar, solo las pruebas del mismo destino físico pueden reducirlos a una sola actualización.
- **Corte de tareas.** La reconciliación local compara la versión de la ejecución y de cada vínculo y guarda estado e historial en una transacción. Antes del corte, un vínculo no comprobado deja de verse; después, la decisión se toma con evidencia vigente a la hora original del corte. Una tarea física sigue visible si conserva un vínculo activo, que es el que se muestra en el tablero. El registro de la ejecución y la generación heredada comparten un bloqueo por tipo y fecha para no generar la misma base o dominio dos veces. La limpieza heredada no cancela ejecuciones del catálogo. La mutación y el acceso a credenciales heredados no utilizan un vínculo de catálogo retirado ni una tarea histórica como autorización. No se eliminan las filas de tareas o programaciones.
- **Barrido de corte.** Se ejecuta en el temporizador diario existente y en el refresco manual autorizado, no en consultas GET ni al guardar una programación. Selecciona hasta 32 ejecuciones abiertas por pasada, prioriza cortes vencidos y usa el reloj de SQL. Lee y aplica la evidencia en la misma transacción. Una consulta a SQL incompleta o fallida no retira tareas; un vínculo comprobado pero sin evidencia válida al corte sí se oculta o retira según la fecha. La 039 separa el instante de verificación del de registro de la prueba. Para un vínculo externo, la revisión disponible debe haberse publicado antes del corte, estar vigente, corresponder al perfil y contener el registro exacto; si el historial de intentos no permite probarlo no se presume que siguiera disponible. La primera revisión después del corte no reabre una ejecución retirada. Falta ensayar el barrido con el catálogo real y verificar la cadencia operativa antes de activarlo.
- **Historia de fuentes al comprobar el corte.** El lector usa la cabecera actual antes del corte y el último evento de la 050 registrado hasta ese instante cuando el corte ya llegó. Considera también fallos y cabeceras retiradas; no busca la última revisión exitosa ni vuelve a la cabecera actual si falta historia. Así, un refresco posterior no retira por error un destino presente al corte, y un éxito posterior no acredita retroactivamente una presencia desconocida. Se mantienen las comprobaciones de configuración, destino, versiones y UUID conocido. El trabajador también omite tareas completadas o canceladas que cambiaron después de leer la cola, antes de pedir evidencia.
  `Test-CatalogTaskCutoffHistoryQa.ps1` pasó **16/16 casos en 370 ms de SQL**, con dos fuentes ERP y dos alias de base sobre un mismo destino físico. Incluye fallos anteriores y posteriores, ausencia de historia, límite exacto del corte, vencimiento, cambios de perfil y supervivencia de un alias cuando el otro pierde evidencia. El fixture histórico de QA usa cuatro de las excepciones de sello INSERT ya revisadas, restauradas antes de las consultas; no suspende inmutabilidad, no consulta fuentes externas y revierte todos sus datos conservando los objetos instalados de la 050. QA independiente aprobó **59 pruebas en siete archivos** de corte, reconciliación, planificación, visibilidad y permisos. La verificación completa del API se repetirá con el candidato conjunto del nuevo ciclo de actualización; no se afirma una carrera real entre sesiones ni un despliegue productivo con estos resultados.
- **Conexión desde Tareas.** Con la lectura del catálogo habilitada, abrir, revelar y copiar requieren una tarea abierta y una asignación vigente. Las personas nombradas prevalecen sobre el rol; poder ver todas las tareas, incluso como superadministrador, no equivale a estar asignado. Se comprueban los permisos existentes de Tareas y el vínculo exacto que representa a la ejecución, sin dar acceso a otras bases que compartan el destino físico. SQL rechaza un vínculo vencido o retirado, evidencia externa vencida y un corte pasado todavía sin reconciliar. Al consultar Key Vault se libera primero la transacción, y se vuelven a comprobar asignación y versiones antes de devolver la contraseña. El registro de auditoría debe persistir antes de la respuesta y contiene identificadores, acción y parte, nunca los valores. Las respuestas no se almacenan en caché; la contraseña se entrega solo en la respuesta de texto a la acción POST explícita. Antes de habilitar el interruptor, publicar también la versión de Tareas que entiende esta respuesta.
- **Generación por día.** El servicio interno `generateCatalogScheduleDay` usa la fecha de negocio de Bogotá como identidad común a la ejecución automática, el refresco y las solicitudes manuales. Un refresco genérico no crea tareas de una frecuencia exclusivamente manual; si se solicita una programación manual concreta, sus destinos se contrastan con todas las programaciones que vencen ese día. La reejecución conserva la identidad y el corte originales. Antes de insertar, SQL bloquea y comprueba la versión de cada programación, el destino físico y todos sus vínculos; una edición concurrente o una operación/asignación incompatible no se transforma en otra tarea. El lector interno obtiene candidatas con alcances y versiones en la misma transacción; no trunca el conjunto como el listado legado. `generateCatalogPersistedScheduleDay` adapta el alcance guardado a los vínculos exactos de la revisión: primero filtra por cliente, dominio, tipo, ambiente y exclusiones, y solo después deduplica. Un conjunto explícito vacío no equivale a todos; un destino fijo ausente queda retenido. Mantiene el conjunto completo de responsables explícitos, distinto por tipo, y no degrada «todas las licencias» si desaparece una requerida. La operación aprobada debe pertenecer a la versión vigente de la programación. El inventario operativo y las entradas HTTP/temporizador ya están conectados en modo catálogo; faltan la alimentación automática con fuentes reales, la evidencia oportuna antes de cada corte y la certificación integral. El cierre de programaciones únicas comprueba el conjunto durable completo descrito más abajo, no sólo la lista heredada.
- **Adaptador de inventario operativo.** `generateCatalogOperationalScheduleDay` convierte la lectura de la 042 en el inventario del programador existente. Exige cobertura, conserva los vínculos no verificables como retenidos y no consulta fuentes después del corte. Para resolver licencias, el servicio necesita una versión de emparejamiento confiable provista por el servidor. El registro de un vínculo ERP vuelve a exigir en SQL que coincidan el UUID, cliente, dominio, base, ambiente, origen, registro y versiones actuales de revisión y perfil. Una reejecución no modifica el historial. La entrada interna aprobada utiliza por defecto la certificación 046; HTTP y el temporizador la alcanzan solo en el modo explícito del catálogo.
- **Cobertura revisada (046).** Un superadministrador activo puede quedar identificado como aprobador de una sola población abierta por ambiente; se conserva el historial y la vigencia no supera 30 días. La aprobación debe provenir de una reconciliación independiente de las fuentes ERP y SAG Admin y de sus vínculos operativos, no de copiar una lista parcial del portal ni de igualar conteos. El resumen es SHA-256 del JSON UTF-8 documentado en `catalogSchedulePopulationDigest`: ambiente, tuplas ordenadas de fuente/rol/versiones de vínculo y perfil, y UUID de vínculos ordenados. No contiene datos de cliente ni credenciales. Una fuente o vínculo nuevo, retirado o sustituido invalida el resumen; una caída temporal puede dejar vínculos existentes no verificables, pero no los elimina ni autoriza sus tareas. No se sembraron aprobaciones ni se abrieron rutas de edición. Falta certificar el conjunto real.
  La migración 046 pasó un ensayo de DDL con reversión y después el ejecutor la verificó en `PortalSAGWeb-TEST`. `Test-CatalogSchedulePopulationCoverageQa.ps1` hizo seis comprobaciones con la consulta real, incluido el vínculo retenido y el retiro o desactivación del aprobador, sin datos sintéticos restantes.
- **Transacción del día certificado.** La entrada interna vuelve a leer la población y las versiones de toda la lista de programaciones, resuelve los destinos físicos y registra los grupos dentro de una sola transacción `SERIALIZABLE`. Obtiene primero los bloqueos compartidos con la ruta heredada, en orden base → dominio. Al terminar vuelve a comparar el reloj SQL con el corte y el vencimiento más temprano de las pruebas usadas por las tareas registradas. Un cambio concurrente o un error en un grupo posterior no deja guardados los anteriores. `Test-CatalogScheduleDayTransactionQa.ps1` verificó el bloqueo y el reloj reales de SQL Server 2019 en tres casos sobre una tabla temporal: éxito, vencimiento y corte. No equivale a una generación completa con datos reales ni a un ensayo de volumen o contención entre sesiones.
- **Intenciones manuales (047).** La solicitud manual queda registrada por ambiente, fecha de Bogotá y versión de la programación; conserva el primer usuario y la hora de SQL en los reintentos. Una edición o un retiro de la aprobación deja la solicitud en el historial, pero evita que el plan la use. La transacción del día vuelve a comparar todas las solicitudes efectivas antes de registrar tareas. El futuro punto de entrada debe comprobar `updates.schedules.generate_tasks` y derivar actor, ambiente y corte del servidor. En `PortalSAGWeb-TEST`, el ejecutor verificó la 047; el ensayo sobre las consultas reales comprobó 10 casos sin datos residuales.
- **Reconciliación manual y automática del mismo destino.** En un día certificado, si la tarea ya cubre los vínculos y programaciones solicitados, se devuelve la referencia existente sin volver a escribirla. Si llega una programación compatible para un vínculo lógico exacto ya activo, SQL vuelve a comprobar el alcance, operación, evidencia física, ERP y licenciamiento aplicable, y añade solo el origen faltante. No cambia representante, responsables, estado, vínculos de conexión ni eventos de registro. Un origen secundario activo para el mismo vínculo puede conservar la visibilidad según las reglas existentes; no crea derechos de conexión nuevos. La prueba de conexión, corte y registro pasó 37 comprobaciones en QA.
- **Alias tardío de un destino ya programado (048).** Un vínculo lógico distinto puede dejar un recibo de procedencia si el destino físico, día, ambiente, operación y responsables coinciden y la prueba vigente de ERP, destino y licenciamiento lo permite. SQL conserva un solo recibo inmutable para la ejecución, el vínculo, la programación y su versión. El recibo no entra en `workflow.task_sources` ni en los vínculos de la tarea: no cambia la lista operativa, las credenciales, el estado, la asignación ni los eventos, y no reactiva un vínculo previamente retirado. Pasaron 21 casos sintéticos en SQL Server 2019 de QA, incluidos el reintento, la ausencia de escrituras de acceso y el rechazo por ambiente, destino, operación, versión o vínculo previo incorrectos.
- **Despacho de generación.** El modo explícito `PORTAL_CATALOG_GENERATION_MODE=catalog` usa el mismo servicio para el temporizador, `POST /api/tasks/generate`, `POST /api/tasks/refresh` y el refresco después de guardar una programación. Requiere ambiente válido, lectura y barrido de corte habilitados y versión de emparejamiento válida. ## Incremento local: cierre de las mutaciones heredadas

`catalogMasterOwnership.ts` centraliza el bloqueo de las mutaciones HTTP de
Dominios, Bases de Datos y Licenciamiento cuando
`PORTAL_CATALOG_READ_ENABLED=true`. Los 16 endpoints conservan autenticación y
permiso de acción antes de responder 409; rechazan incluso a `super_admin`
antes de leer el cuerpo, buscar destinos, escribir, borrar en cascada o acceder
a secretos. Las modificaciones de estado de licencias forman parte de PUT.
No modifica permisos ni DDL, no impide la conciliación interna y no bloquea
consultas/copias/revelaciones autorizadas desde tareas. Con flag apagado o
ausente se mantiene el comportamiento anterior.

La matriz reprodujo primero los **16 fallos** (50 casos ya pasaban). Con el
cambio pasaron **66/66 casos nuevos**, **152/152 pruebas enfocadas** de Desarrollo
y **156/156 en ocho archivos** de QA independiente. El build del API pasó. La
suite completa posterior pasó **1.506/1.506 en 160 archivos, 194,60 s**. Son
resultados locales; no se activó el flag ni se publicó este incremento en
producción. Para revertir el código se restaura el paquete anterior, sin borrar
historia ni cambiar permisos; eso recuperaría también la posibilidad de
mutaciones heredadas al activar lectura del catálogo.
