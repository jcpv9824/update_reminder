## Flujos integrados

- **Configuración → Conexiones.** Reutiliza perfiles SQL existentes. El registro distingue los ERP que suministran clientes de SAG Admin. Guardar un vínculo sólo crea un borrador. **Verificar** necesita el permiso de prueba y comprueba TLS, permisos de solo lectura, esquema y una fila como máximo, sin mostrar datos. **Activar** necesita además el permiso de edición, repite la prueba y guarda la certificación sólo si el vínculo y el perfil siguen siendo los mismos. También permite revalidar una fuente activa cuando el perfil cambió; no cambia su rol ni la sustituye. Verificar o activar no publica revisiones ni cambia permisos de la base remota.
- **Clientes.** Vista de sólo lectura, con filtros iniciales Activos y En SAG Web. El selector parte de todas las fuentes ERP autorizadas para quien consulta. Las fuentes fallidas se muestran como desactualizadas o no disponibles, no como clientes inactivos ni fuera de SAG Web. La vista anterior se conserva hasta el corte deliberado; no es un fallback ante errores del catálogo nuevo.
- **Acceso.** Los endpoints requieren sesión y permiso de Portal. Además, el backend comprueba el acceso a cada ERP en SQL, no a partir de los filtros enviados por el navegador. La migración 034 no siembra nuevos accesos. El contrato de lectura no devuelve identificaciones en claro, contraseñas, hosts ni cadenas de conexión.
- **Preparación de una revisión.** El servicio de carga sólo admite vínculos activos del entorno indicado. Exige una lectura externa completa en una transacción `SNAPSHOT` y conserva la diferencia entre «sin registros» y «no disponible». Entrega al publicador la versión del vínculo y del perfil, el identificador interno de fila, el estado normalizado y un token HMAC del documento; no entrega el documento original. Antes de abrir la fuente, SQL asigna un número de intento que ordena resultados concurrentes independientemente de su hora de finalización. Las coincidencias de SAG Admin sólo se consideran de un emisor cuando existe un mapeo revisado, y las filas sin emisor no permiten afirmar que otros clientes están fuera de SAG Web.
- **Actualización explícita por fuente.** `POST /api/settings/integrations/catalog-sources/{sourceId}/refresh` recibe únicamente `{}`. Requiere `super_admin` activo y permisos de ver, probar y editar Conexiones; limita las solicitudes y no abre las demás fuentes. SQL verifica de nuevo operador, vínculo y perfil en cada transacción. Solo una revisión sellada reemplaza la actual y la publicación exitosa audita el ID del operador sin valores del origen. La ruta no modifica la pantalla ni programa ejecuciones periódicas. Para SAG Admin, `PORTAL_CATALOG_SAG_ISSUER_MAP` admite pares revisados `countryId`/`issuerScope`; no permite declarar cobertura negativa desde ese mapa.
- **Evidencia de SAG Admin.** La migración 035 permite sellar y conservar el dominio candidato, el ambiente, las letras de licenciamiento aceptadas y las fechas conocidas de inicio por ambiente. El SELECT emite únicamente el hostname y los tres días autorizados; no devuelve la URL completa ni el JSON original. Ausencia o invalidez se conservan como desconocidas. El hostname por sí solo no habilita una conexión ni acredita una base o un despliegue.
- **Detalle de Clientes.** Dominio y licenciamiento se consultan en rutas separadas con los permisos existentes de cada opción. El backend resuelve el ID opaco del cliente sólo en fuentes ERP autorizadas y cruza revisiones selladas por emisor, tipo y token exactos. La evidencia incompleta se marca; una revisión vencida no se presenta como actual, y una consulta sin coincidencia no acredita ausencia sin cobertura. Dominios se muestran como texto y agrupados por nombre dentro del mismo cliente, con observaciones separadas por ambiente; no habilitan acceso o programación.
- **Correspondencia de licencias.** Con la migración 041 un operador puede registrar en `settings.catalog_sag_license_module_approvals` una correspondencia revisada de una letra hacia un módulo existente. SQL exige fuente SAG Admin activa y certificada, versiones exactas del vínculo y del perfil, identificador de aprobación y operador. El detalle muestra el nombre y la descripción de módulos activos solo para los códigos observados. Una letra sin equivalencia queda como «Correspondencia no verificada». No se crean módulos ni se sugieren equivalencias por similitud. Las aprobaciones no se sobrescriben; cualquier cambio de la fuente o del perfil exige volver a aprobarlas. El resolver interno solo prepara IDs de licencia cuando el cliente tiene evidencia vigente, el dominio y ambiente coinciden y no hay observaciones ambiguas. No devuelve los IDs internos al navegador ni habilita por sí solo el generador de tareas.
- **Registro físico.** La migración 036 separa cada relación lógica de un destino SQL o web acreditado. SQL usa una instancia certificada y el GUID leído con la cuenta y TLS aprobados; web usa un identificador de despliegue acreditado, no el texto de la URL. Si cambia la ruta se retira la prueba y volver atrás no la rehabilita. Si cambia el perfil SQL, su versión deja de coincidir. La huella histórica del nombre sólo sirve para rechazar una colisión de GUID con catálogos distintos: no permite unir destinos por nombre. Un cambio de nombre SQL necesita un procedimiento de continuidad antes de volver a aceptar el destino; no se reasigna silenciosamente.
- **Vínculo operativo.** La 042 registra por separado el cliente del catálogo, su correspondencia con el maestro operativo y cada vínculo ERP de un dominio o de una base. Los vínculos tienen UUID estable; las aprobaciones no se sobrescriben y se atan a la versión certificada del origen y del perfil. Un refresco normal que conserva el registro exacto activo y la identidad del cliente no cambia el UUID. Si cambia el perfil, se requiere una aprobación adicional; si se retira el cliente o el vínculo, la historia se conserva. El lector interno conserva vínculos abiertos no verificables y rechaza una lectura de más de 5.000 vínculos en lugar de devolver un conjunto truncado. Una aprobación no certifica el servidor físico, no asigna licencias y no otorga acceso a credenciales.
- **Dominios compartidos.** La 043 permite la misma URL HTTPS normalizada en clientes o ambientes distintos. Cada relación conserva su propio ID y las bases asociadas. Una URL no puede repetirse dentro del mismo cliente y ambiente mientras los registros no estén eliminados. El API devuelve un conflicto controlado para esa colisión. La coincidencia de URL nunca une enlaces automáticamente: al planificar, solo las pruebas del mismo destino físico pueden reducirlos a una sola actualización.
- **Corte de tareas.** La reconciliación local compara la versión de la ejecución y de cada vínculo y guarda estado e historial en una transacción. Antes del corte, un vínculo no comprobado deja de verse; después, la decisión se toma con evidencia vigente a la hora original del corte. Una tarea física sigue visible si conserva un vínculo activo, que es el que se muestra en el tablero. El registro de la ejecución y la generación heredada comparten un bloqueo por tipo y fecha para no generar la misma base o dominio dos veces. La limpieza heredada no cancela ejecuciones del catálogo. La mutación y el acceso a credenciales heredados no utilizan un vínculo de catálogo retirado ni una tarea histórica como autorización. No se eliminan las filas de tareas o programaciones.
- **Barrido de corte.** Se ejecuta en el temporizador diario existente y en el refresco manual autorizado, no en consultas GET ni al guardar una programación. Selecciona hasta 32 ejecuciones abiertas por pasada, prioriza cortes vencidos y usa el reloj de SQL. Lee y aplica la evidencia en la misma transacción. Una consulta a SQL incompleta o fallida no retira tareas; un vínculo comprobado pero sin evidencia válida al corte sí se oculta o retira según la fecha. La 039 separa el instante de verificación del de registro de la prueba. Para un vínculo externo, la revisión disponible debe haberse publicado antes del corte, estar vigente, corresponder al perfil y contener el registro exacto; si el historial de intentos no permite probarlo no se presume que siguiera disponible. La primera revisión después del corte no reabre una ejecución retirada. Falta ensayar el barrido con el catálogo real y verificar la cadencia operativa antes de activarlo.
- **Conexión desde Tareas.** Con la lectura del catálogo habilitada, abrir, revelar y copiar requieren una tarea abierta y una asignación vigente. Las personas nombradas prevalecen sobre el rol; poder ver todas las tareas, incluso como superadministrador, no equivale a estar asignado. Se comprueban los permisos existentes de Tareas y el vínculo exacto que representa a la ejecución, sin dar acceso a otras bases que compartan el destino físico. SQL rechaza un vínculo vencido o retirado, evidencia externa vencida y un corte pasado todavía sin reconciliar. Al consultar Key Vault se libera primero la transacción, y se vuelven a comprobar asignación y versiones antes de devolver la contraseña. El registro de auditoría debe persistir antes de la respuesta y contiene identificadores, acción y parte, nunca los valores. Las respuestas no se almacenan en caché; la contraseña se entrega solo en la respuesta de texto a la acción POST explícita. Antes de habilitar el interruptor, publicar también la versión de Tareas que entiende esta respuesta.
- **Generación por día.** El servicio interno `generateCatalogScheduleDay` usa la fecha de negocio de Bogotá como identidad común a la ejecución automática, el refresco y las solicitudes manuales. Un refresco genérico no crea tareas de una frecuencia exclusivamente manual; si se solicita una programación manual concreta, sus destinos se contrastan con todas las programaciones que vencen ese día. La reejecución conserva la identidad y el corte originales. Antes de insertar, SQL bloquea y comprueba la versión de cada programación, el destino físico y todos sus vínculos; una edición concurrente o una operación/asignación incompatible no se transforma en otra tarea. El lector interno obtiene candidatas con alcances y versiones en la misma transacción; no trunca el conjunto como el listado legado. `generateCatalogPersistedScheduleDay` adapta el alcance guardado a los vínculos exactos de la revisión: primero filtra por cliente, dominio, tipo, ambiente y exclusiones, y solo después deduplica. Un conjunto explícito vacío no equivale a todos; un destino fijo ausente queda retenido. Mantiene el conjunto completo de responsables explícitos, distinto por tipo, y no degrada «todas las licencias» si desaparece una requerida. La operación aprobada debe pertenecer a la versión vigente de la programación. Todavía faltan el proveedor de inventario completo, la conexión al temporizador y a HTTP, y la certificación integral del corte. La finalización de programaciones únicas debe considerar todas las tareas del catálogo y las retenidas, no solo la lista heredada.
- **Adaptador de inventario operativo.** `generateCatalogOperationalScheduleDay` convierte la lectura de la 042 en el inventario del programador existente. Exige cobertura, conserva los vínculos no verificables como retenidos y no consulta fuentes después del corte. Para resolver licencias, el servicio necesita una versión de emparejamiento confiable provista por el servidor. El registro de un vínculo ERP vuelve a exigir en SQL que coincidan el UUID, cliente, dominio, base, ambiente, origen, registro y versiones actuales de revisión y perfil. Una reejecución no modifica el historial. La entrada interna aprobada utiliza por defecto la certificación 046. Aún no se llama desde HTTP ni desde el temporizador.
- **Cobertura revisada (046).** Un superadministrador activo puede quedar identificado como aprobador de una sola población abierta por ambiente; se conserva el historial y la vigencia no supera 30 días. La aprobación debe provenir de una reconciliación independiente de las fuentes ERP y SAG Admin y de sus vínculos operativos, no de copiar una lista parcial del portal ni de igualar conteos. El resumen es SHA-256 del JSON UTF-8 documentado en `catalogSchedulePopulationDigest`: ambiente, tuplas ordenadas de fuente/rol/versiones de vínculo y perfil, y UUID de vínculos ordenados. No contiene datos de cliente ni credenciales. Una fuente o vínculo nuevo, retirado o sustituido invalida el resumen; una caída temporal puede dejar vínculos existentes no verificables, pero no los elimina ni autoriza sus tareas. No se sembraron aprobaciones ni se abrieron rutas de edición. Falta certificar el conjunto real.
  La migración 046 pasó un ensayo de DDL con reversión y después el ejecutor la verificó en `PortalSAGWeb-TEST`. `Test-CatalogSchedulePopulationCoverageQa.ps1` hizo seis comprobaciones con la consulta real, incluido el vínculo retenido y el retiro o desactivación del aprobador, sin datos sintéticos restantes.
- **Transacción del día certificado.** La entrada interna vuelve a leer la población y las versiones de toda la lista de programaciones, resuelve los destinos físicos y registra los grupos dentro de una sola transacción `SERIALIZABLE`. Obtiene primero los bloqueos compartidos con la ruta heredada, en orden base → dominio. Al terminar vuelve a comparar el reloj SQL con el corte y el vencimiento más temprano de las pruebas usadas por las tareas registradas. Un cambio concurrente o un error en un grupo posterior no deja guardados los anteriores. `Test-CatalogScheduleDayTransactionQa.ps1` verificó el bloqueo y el reloj reales de SQL Server 2019 en tres casos sobre una tabla temporal: éxito, vencimiento y corte. No equivale a una generación completa con datos reales ni a un ensayo de volumen o contención entre sesiones.
- **Bloqueo de activación: ejecución manual y automática del mismo destino.** La clave física del día no cambia al agregar una programación, pero una reejecución idéntica exige el mismo conjunto de orígenes. Antes de conectar HTTP o el temporizador, confirmar los dos órdenes (manual → automática y automática → manual) con la misma operación y responsables. La solución debe conservar la intención manual autorizada y reconciliar orígenes compatibles sin duplicar trabajo, volver a asignar, reabrir tareas completadas ni cambiar su vínculo representativo. Mantener el rechazo de operaciones o responsables incompatibles y comprobar que un choque no se convierta en autorización de acceso a otra base.
- **Visibilidad inmediata.** Las consultas operativas de tareas utilizan el vínculo vigente, no solo el último estado persistido por el barrido. Revalidan en SQL el ambiente, el destino físico y la relación ERP aprobada. Si ningún vínculo activo sigue vigente, se oculta la tarea abierta sin modificar su historia; si queda un alias válido, puede representarla. Un filtro puede encontrar la tarea a través de un alias vigente, pero no cambia el representante que se muestra y al que se aplica el acceso a conexión. El historial completado conserva su proyección dentro de su propio ambiente y los accesos de rol y asignación se evalúan por separado. Las mutaciones heredadas vuelven a verificar el representante original en el instante de escribir; no se amplían al alias alternativo. Cuando el corte se cumple sin reconciliar, la tarea queda fuera de la vista operativa hasta el resultado del corte.
- **Operación aprobada.** La 044 registra un ID opaco de operación, el ambiente y la versión exacta de cada programación. La aprobación queda atribuida a un superadministrador activo; no hay regla automática basada en el título de la programación ni permiso de escritura para el principal normal de runtime. `generateApprovedCatalogOperationalScheduleDay` lee ese ID del mismo conjunto versionado que usa para planificar. El registro vuelve a comprobar la aprobación dentro de su transacción; una edición, retiro, cambio de ambiente u operación distinta impiden crear la tarea. Las ejecuciones históricas no se actualizan para adaptar sus IDs a la nueva regla.
- **Licencias para planificar y registrar.** El lector interno usa el cliente opaco, su origen ERP autorizado, la versión de la clave de emparejamiento y el hostname y ambiente exactos. Una evidencia ausente, vencida, ambigua o con códigos sin equivalencia sigue siendo desconocida, no una lista vacía. Dentro de la transacción, cada vínculo de una programación por licencias debe seguir teniendo el mismo conjunto completo de módulos, según las revisiones actuales de ERP y SAG Admin y sus equivalencias aprobadas. SQL aplica los filtros persistidos, incluyendo «alguna» o «todas», y comprueba el vínculo del dominio padre para las bases. Se usa el primer vencimiento entre las pruebas aplicables y el corte de la tarea; si alguna comprobación falla, no queda registrada la tarea ni su evento. Esta comprobación interna no habilita rutas ni temporizadores por sí sola.
  `Test-CatalogExecutionLicenseProofQa.ps1` ejecutó la consulta del repositorio en SQL Server 2019 de QA: 10 escenarios aprobados, cero filas de prueba restantes. Incluye equivalencia exacta, primera expiración, «alguna»/«todas», exclusión, fallo de actualización SAG, hostname con guiones y rechazo de una base al retirar su dominio padre. Es un ensayo sintético; no acredita la cobertura de las fuentes reales ni el flujo completo de generación.
- **Continuidad del vínculo 042.** El acceso vuelve a consultar la aprobación vigente y, para una contraseña, compara también el testigo de la fuente tras leer Key Vault. Después de escribir la auditoría, se vuelve a comprobar la vigencia con el reloj de SQL; si falta evidencia, la transacción revierte y no se devuelve el dato. El testigo se queda en el backend. El corte exige que el vínculo, la correspondencia del cliente y la aprobación existieran a la hora evaluada; una aprobación posterior no se acepta retroactivamente. Si no se puede probar el historial del origen o destino, el vínculo no se da por verificado. Un UUID conocido de la 042 no puede tratarse como un vínculo local ni al registrar una tarea ni al acceder a la conexión o verificar el corte. No se cambiaron roles ni permisos del catálogo.
- **Conteo de usuarios.** La migración 037 agrega un registro local de certificaciones por destino físico, sin claves ni datos de conexión. El servicio interno vincula la prueba al perfil de solo lectura, a su versión exacta y a la identidad física; no reutiliza credenciales de tareas. El adaptador admite una vista de agregado aprobada o un contrato certificado de `dbo.usuarios`, y verifica identidad, permisos y conteo en la misma conexión TLS. El reporte actual puede agregar conteos a las filas autorizadas del maestro existente y suma una sola vez cada base física; no cuenta personas únicas entre bases. Se vuelve a comprobar la certificación y sus vínculos antes y después de la consulta. Si no se puede acreditar o consultar una base, se muestra «No pudimos obtener los datos de esta base de datos.» sin tratar el fallo como cero. Mientras no se migren los consumidores del catálogo, los nombres y las relaciones del reporte no vienen del ERP. El envío enriquecido exige destinatarios activos con permiso vigente de reportes y vuelve a comprobarlos antes de enviar.

La API requiere un entorno explícito `PORTAL_SAG_ENVIRONMENT=qa` o `production`. El lector requiere una versión de la clave de emparejamiento en `PORTAL_CATALOG_MATCH_KEY_VERSION`, coincidente con las revisiones publicadas. Esto no es la clave ni autoriza guardarla en el repositorio.

La actualización explícita lee exclusivamente la versión de Key Vault indicada en `PORTAL_CATALOG_MATCH_KEY_SECRET_VERSION` del secreto `PORTAL_CATALOG_MATCH_KEY_SECRET_NAME`. Debe representar 32 bytes generados con un generador criptográfico y codificados en hexadecimal. La 038 no inscribe valores: un operador autorizado debe registrar una sola vez, antes de cualquier revisión del entorno, la versión numérica, los 16 bytes de la versión exacta de Key Vault y la prueba HMAC producida por `buildCatalogMatchKeyEvidence`; debe usar el bloqueo transaccional exclusivo `portal-sag:catalog-customer-publication:<entorno>`. SQL no guarda la clave, y el publicador exige que coincidan versión, referencia y prueba antes de reservar, registrar un fallo o publicar. No se puede sustituir la inscripción ni tomar la última versión por defecto. Este flujo no rota claves ni inscribe automáticamente. Antes de habilitar, falta hacer la inscripción real y certificar las conexiones. La protección de inmutabilidad no sustituye los controles de acceso al principal de base de datos que tiene privilegios de propietario.

## Antes de activar

1. Certificar el esquema 031–046 en QA. `Apply-PortalSAGWeb-PendingMigrationsThroughSession.ps1 -Environment qa -IncludeCatalog` suma 031–046 al paquete. Sus hashes están fijados sobre texto LF. Las consultas de tareas requieren la vista de la 042; la carga de dominios compartidos, la 043; y el programador, las operaciones versionadas 044–045 y la autoridad de cobertura 046. Activar filtros y programación solo cuando las correspondencias estén certificadas.
2. Integrar y certificar la carga de revisiones con cuentas de sólo lectura, credenciales referenciadas y pruebas de aislamiento por fuente. Un borrador no cuenta como fuente habilitada y un endpoint que responde no equivale a un catálogo alimentado.
3. Conectar y certificar las relaciones cliente–dominio–base, el catálogo de licencias, la deduplicación en la programación y en tareas, y el reporte de usuarios activos. El código de comparación, corte y conteo no habilita por sí solo el programador, no identifica destinos físicos sin evidencia aprobada y no prueba el esquema `usuarios` de una base remota. Verificar de punta a punta en QA la asignación, el corte y los registros de apertura, revelación y copia usando un perfil de prueba, no credenciales reales de clientes.
   La revisión ERP y el registro físico aún no identifican por sí solos el mismo vínculo lógico. Poblar y certificar la correspondencia aprobada de la 042 antes de habilitar consumidores; nunca inferirla por nombre de cliente, hostname, nombre de base o coincidencia casual de identificadores. Los listados heredados sin paginación tienen un tope: no constituyen un inventario completo. El proveedor futuro deberá comprobar las versiones de las revisiones y de las equivalencias utilizadas en cada planificación, y volver a comprobar el vínculo al registrar o autorizar la tarea. Con vínculos ya registrados, no ejecutar el reemplazo masivo heredado de la 021: elimina filas de maestros referenciadas por estas claves foráneas. La carga del catálogo debe reconciliar sin borrar identidades ni historia.
   No reinstalar el índice global antiguo si ya existen nombres compartidos. El rollback del API no borra relaciones ni cambia el índice; un eventual rollback del esquema requiere conciliar las colisiones globales con el responsable y preparar una recuperación separada.
4. Certificar en QA el corte de clientes una vez migrados sus consumidores. Al activar la lectura del catálogo, el servidor rechaza creación, edición, borrado, desactivación y reactivación por el API heredado, incluso para administradores; las lecturas heredadas se mantienen para los módulos que aún dependen de ellas. Verificar permisos, historial, tareas, reportes y reversión antes de habilitar los interruptores en producción.

## Preflight de un perfil inicial

Después de compilar el API, ejecutar desde `api/`: `node scripts/verify-catalog-origin.cjs <archivo-env-fuera-del-repo> <erp_v1|sag_admin_v1>`. El comando sólo devuelve el contrato y el estado; no copia el archivo, no publica datos ni modifica la configuración. El servidor debe ser un hostname con puerto numérico opcional (`servidor,puerto` o variable separada). Las credenciales nunca se pasan por argumentos.

Si el perfil local especifica una instancia, el puerto debe ser explícito: `servidor\INSTANCIA,puerto` o `servidor,puerto\INSTANCIA` para el formato local anterior. El transporte solo conecta al hostname y puerto dados, sin SQL Browser ni redirecciones. Después de validar TLS comprueba la instancia en la misma transacción de solo lectura antes de consultar el esquema o la proyección. Un puerto contradictorio, un cambio de destino o una instancia inesperada termina el preflight sin leer datos de clientes.

En la última prueba local del ERP, el puerto respondió, la conexión TLS se completó y se inició la transacción `SNAPSHOT`, pero el nombre devuelto por `SERVERPROPERTY('InstanceName')` no coincidió con la instancia indicada. El preflight no consultó el esquema ni registros. Validar el puerto y la identidad esperada con el administrador del origen antes de volver a ejecutar; no desactivar la comprobación ni replantear permisos por este resultado.

El inventario actual de Azure no tiene un API o frontend dedicado de QA. El workflow principal apunta al API de producción, así que no se usa como prueba de QA. La base `PortalSAGWeb-TEST` sí está disponible; al revisar, no tenía perfiles SQL guardados para certificar.

El detalle conserva los códigos observados; para asignarles nombres y usarlos como filtros de actualización hace falta una correspondencia verificada, no una unión por coincidencia aproximada de nombre.
